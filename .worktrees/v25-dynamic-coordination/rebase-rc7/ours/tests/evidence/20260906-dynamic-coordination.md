# Dynamic shared-workflow extraction

Two concurrently delivered modules exposed the same practical coordination boundary: source owners could continue their module work, but shared registration and integration work needed one owner without restarting the original missions. The authorized v2.5 outcome is an execution decomposition of those original goals, not a replacement product architecture or a second approval of unchanged scope.

The executable assignment remains in `resources/orchestrator.json#workflowTopologies.coordination` and `scripts/workflow-coordination.mjs`. Peers enrol through their own session mutation. A preparation freezes the coordinator, donor and affected consumer mission scopes, derives the new producer's exact authorized subset, and names only the dependent logical nodes. Activation shares a Source lock with write admission and durable worker reservation. A broad donor claim can exclude a transferred subtree; an older admission remains valid for an unaffected sibling, while a request spanning the excluded subtree is refused. Canonical Git repository identity and physical checkout paths prevent aliases from creating another owner.

The source consumer first imports the original current accepted producer, then records its own incorporation intent and ordinary Git merge. The receipt checks the frozen old head, producer head, merge parents, intended tree and message. Normal hooks and signing remain active. Conflicts, dirty checkouts, wrong heads and altered hook results preserve the checkout and refuse acceptance. A process stopped after its merge but before receipt retention can resume only that exact intent; it does not merge again or reset user work.

Completion reads the original accepted peer missions. It requires incorporation and subsequent consumer regression at the affected terminal head. Combined proof additionally joins actual accepted API and browser verification to per-role before/after runtime observations, including served heads, measured endpoints, serving checkout identity and the complete producer/consumer contribution tuple. Context heads, copied success labels, legacy output-only bundles and an aggregate of unrelated passing tests cannot establish this proof.

The portable tests include separate-process transfer/admission races; competing stale-lock recovery; scope changes after preparation; broad-to-subtree transfer; absolute and symlink ownership aliases; current producer and import tampering; actual Git hooks, conflicts, renames, deletions and dirty retry preservation; and a killed incorporation process. The authentic fixture chains use ordinary current request open, worker acquisition and attempt acceptance. Their API calls execute source-owned suites. Wide and narrow browser captures prove the interface audit; the browser UAT runs the narrow journey against separate frontend/backend repositories with a real HTTP proxy. These are runtime regression fixtures, not product UAT or evidence that either module has shipped.

A damaged `.recovery` marker remains an explicit fail-closed boundary requiring owner inspection. The lock code does not claim automatic recovery after the recovery owner itself crashes. Accepted historical evidence remains intact; extraction does not permit rewriting a peer ledger or importing source-write authority.

Dispatch guidance also fixes two observed omissions at existing homes: generated briefs point to the canonical output contract appropriate to the current status, and the nested-return handoff names the existing parent `worker-slots resume` transition before any waiting output is edited. Old workflow handling cites the current archive/fresh-session law, without restoring an execution adapter. The current single-repository portfolio tuple remains a supported representation.

Release validation and exact candidate hashes are retained in the isolated candidate's manifest and validation record. This note describes the tested boundaries and does not claim publication.
