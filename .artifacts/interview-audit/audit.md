# Audit checklist chấm interview (fullstack / framework-foundation)

Mỗi câu: checklist (Sonnet gen→review) · 5 ví dụ trả lời (xuất sắc→kém) · điểm 3 grader (Sonnet/Haiku/flash-lite) + feedback. Điểm = số-ý-phủ ÷ tổng. Để so sánh grader + tinh chỉnh checklist.

## 0-question · kind=theory

**Câu hỏi:** In an interview, someone hands you a service that calls new to instantiate its own dependencies right inside the constructor. Explain to them: what problems this style causes as the system grows (hard to test, hard to swap implementation, loss of sharing, fragile initialization order), and what you gain instead by letting an IoC container create and wire the dependencies for you. Talk through each benefit yourself — don't just rattle off buzzwords.

**Checklist:**

| # | Checkpoint |
|---|---|
| 1 | Chỉ ra vấn đề tight coupling: gọi new bên trong constructor hard-wire consumer vào một concrete implementation cụ thể, muốn swap implementation khác phải sửa code của consumer |
| 2 | Chỉ ra vấn đề hard to test: dependency được tạo bên trong nên không thể inject mock/stub từ bên ngoài, test bị ràng buộc với real object và không thể isolate unit |
| 3 | Chỉ ra vấn đề loss of sharing: mỗi lần new tạo ra instance riêng biệt, không thể share state hoặc expensive resource giữa các consumer |
| 4 | Chỉ ra vấn đề fragile initialization order: khi dependency graph phức tạp, việc hand-wire thứ tự khởi tạo đúng trở nên dễ vỡ và khó maintain |
| 5 | Giải thích cách IoC container hoạt động: consumer chỉ declare dependency qua constructor parameter type, container đọc type đó, build dependency graph, tạo instances theo đúng thứ tự và inject vào |
| 6 | Nêu lợi ích testability khi dùng IoC: dễ dàng inject mock/stub trong test để isolate unit under test |
| 7 | Nêu lợi ích loose coupling khi dùng IoC: có thể swap implementation mà không cần sửa code consumer |
| 8 | Nêu lợi ích lifecycle management khi dùng IoC: container quản lý lifecycle và có thể share singleton instance giữa các consumer |

| L1 | Okay, so when you call `new` right inside the constructor, you're basically saying "I'm going to create my own dependencies myself." That sounds simple at first, but it creates four major headaches as the system grows.  First, **tight coupling**—you've hard-wired yourself to one concrete class. If I want to swap in a different implementation, say a `FastCatService` instead of `CatService`, I have to crack open that constructor and edit it. That violates the open-closed principle.  Second, **testing becomes a nightmare**. Because the dependency is instantiated inside, I can't inject a mock or stub from the outside. My unit test is forced to use the real `CatService`, which might hit a database or network, so I'm not testing in isolation anymore.  Third, **you lose sharing**. Every time you call `new`, you get a fresh instance. If `CatService` holds expensive resources—like a connection pool or cache—you're duplicating that cost everywhere, instead of sharing one singleton.  Fourth, **initialization order becomes fragile**. Once you have a deep dependency graph—A needs B, B needs C, C needs D—you have to manually ensure the right order. Miss one step, and you get null references or half-initialized objects.  Now, when you let an IoC container handle it, the consumer just declares "I need a `CatService`" via a constructor parameter. The container reads that type, builds the entire dependency graph, creates instances in the correct order, and injects them. You get **testability** for free—just pass in a mock. You get **loose coupling**—swap implementations in the container config, zero changes to the consumer. And you get **lifecycle management**—the container can share a singleton across the app. That's inversion of control: the power to create moves from the consumer to the container, and your code becomes modular and maintainable. | 100% | 100% | 100% | ✅ đủ |
